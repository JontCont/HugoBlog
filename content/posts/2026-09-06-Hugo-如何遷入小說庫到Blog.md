## 前言

小說的創作資料和技術 Blog 有不同的生命週期。小說專案需要保存草稿、canon、章節任務與進度；公開網站只應顯示可以讓讀者閱讀的內容。

這篇記錄一個簡潔的整合方式：讓 `blog-novelist` 負責小說閱讀器與章節資料，使用 GitHub Pages 發布；`blog-hugo` 只保留「小說庫」入口，以 iframe 載入公開閱讀器。

---

## 一、為什麼不直接 iframe GitHub Repository？

一開始最直覺的想法，是把 GitHub repository 頁面放進 iframe。實際上不可行，因為 GitHub repository 頁面會回傳防嵌入標頭：

```text
X-Frame-Options: deny
Content-Security-Policy: frame-ancestors 'none'
```

瀏覽器會拒絕把這種頁面嵌入其他網站。因此需要一個可被 iframe 載入的公開靜態頁面，GitHub Pages 正好能負責這件事。

## 二、小說專案要提供哪些公開檔案？

在 `blog-novelist` 根目錄建立 GitHub Pages 的入口：

```text
blog-novelist/
├── .nojekyll
├── index.html
├── reader/
│   ├── index.html
│   └── library.json
└── novels/
    └── gambler/
        └── chapters/
            └── drafts/
                └── 01.md
```

其中：

- `index.html` 可將根網址導向 `reader/`。
- `.nojekyll` 避免 GitHub Pages 以 Jekyll 處理靜態檔案。
- `reader/index.html` 負責書架、類型 Tag、章節目錄與正文閱讀。
- `reader/library.json` 列出要公開的作品、封面、類型、描述與章節來源。

`library.json` 的最小範例：

```json
{
  "title": "小說庫",
  "novels": [
    {
      "slug": "gambler",
      "title": "賭徒",
      "genre": "恐怖驚悚",
      "chapters": [
        {
          "number": 1,
          "title": "賭徒",
          "source": "../novels/gambler/chapters/drafts/01.md"
        }
      ]
    }
  ]
}
```

> 公開前要先確認章節是否適合發布。不要把「草稿檔存在」當成「可以公開」的判斷條件；建議未來用專屬發布清單控制章節是否進入 `library.json`。

## 三、設定 GitHub Pages

進入 `blog-novelist` repository：

1. 開啟 **Settings** → **Pages**。
2. Source 選擇 **Deploy from a branch**。
3. Branch 選擇 `master`。
4. Folder 選擇 `/(root)`。
5. 按 **Save**，等待第一次 build 完成。

完成後，閱讀器網址會是：

```text
https://jontcont.github.io/blog-novelist/reader/
```

先直接在瀏覽器開啟這個網址，確認 `reader/`、`reader/library.json` 與章節 Markdown 都能回應 `200`。這一步成功後，才開始調整 Hugo。

## 四、用 Hugo 參數管理閱讀器網址

iframe 來源不要硬編碼在 Markdown。把公開網址集中放在 `hugo.toml` 的 `[params]`：

```toml
[params]
  novelReaderURL = 'https://jontcont.github.io/blog-novelist/reader/'
```

好處是未來換成其他網域、測試站或新版閱讀器時，只要改一個設定值。

在小說庫專用版型讀取該參數：

```go-html-template
{{ define "main" }}
  <section class="novel-library-shell">
    {{ with site.Params.novelReaderURL }}
      <iframe
        class="novel-reader-frame"
        src="{{ . }}"
        title="{{ $.Title }}"
        loading="eager"
      ></iframe>
    {{ end }}
  </section>
{{ end }}
```

內容頁只保留路由與 layout：

```toml
+++
title = '小說庫'
slug = 'novels'
url = '/novels/'
layout = 'novel-library'
comments = false
+++
```

## 五、為什麼要用專用 layout？

一般 `page.html` 會輸出文章標題、說明、文章卡片與頁尾。如果直接在一般頁面放 iframe，閱讀器會被包在卡片內，還會和小說庫本身的標題重複。

為 `/novels/` 建立 `novel-library` 專用 layout 後，可以：

- 直接讓 iframe 成為主要內容。
- 移除一般文章卡與重複標題。
- 在小說庫頁移除 `site-shell` 的最大寬度和內距，提供全幅閱讀區。
- 只在小說庫頁隱藏網站頁尾，避免閱讀器下方出現不必要的大型區塊。

這些設定都必須以專用 body class 或 layout 判斷限制範圍，避免影響一般文章、分類頁與關於頁。

## 六、iframe 高度與響應式設定

有些主題會把所有 iframe 當成影片，套用 `height: auto` 或固定比例。小說內文很長，這種規則會把閱讀器壓成很小的視窗。

可在 Hugo 端對小說閱讀器設定專屬 class：

```scss
.novel-library-page .site-shell {
  max-width: none;
  padding: 0;
}

.novel-library-shell .novel-reader-frame {
  display: block;
  width: 100%;
  height: calc(100vh - 61px);
  min-height: 620px;
  border: 0;
}
```

`calc(100vh - 61px)` 會讓閱讀區由網站導覽列下方延伸到可視畫面底部。閱讀器自身仍可在 iframe 內垂直捲動，避免外層頁面與內文搶走版面。

## 七、上線前檢查

完成後可依序確認：

1. 直接開啟 GitHub Pages reader，作品與章節能載入。
2. 在 Hugo 本機執行建置。
3. 開啟 `/novels/`，確認 iframe 來源是公開 HTTPS 網址，而不是 `127.0.0.1`。
4. 測試桌機與行動版的作品卡、快速查詢 Tag、章節目錄與正文閱讀。
5. 執行 production build 後再推送主站。

```powershell
hugo --gc --minify
```

本機開發階段可用 Python 靜態伺服器預覽 reader；但公開部署後，iframe 必須指向 GitHub Pages。`127.0.0.1` 只代表瀏覽器所在的那一台電腦，其他讀者無法連線。

## 結論

把小說閱讀器與 Hugo Blog 分開部署，可以讓創作資料維持在小說專案，而公開站只負責導覽與閱讀入口。GitHub Pages 提供可嵌入的靜態來源，Hugo 的參數化網址則讓部署環境切換維持簡單。

這種架構適合先以少量作品驗證閱讀流程。作品與章節增加後，再將 `library.json` 改成由明確的發布清單自動產生，就能保持創作與發布的界線。
